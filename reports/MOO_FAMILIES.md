# Семейства MOO: обоснование выбора и этап 1

Этап 1 — первичный отбор представителей и адаптаций восьми семейств многокритериальной оптимизации (MOO) на KuaiRand в рамках протокола B. Экспериментальные строки этого отчёта относятся только к валидационной выборке; TEST в этапах MOO не использовался.

Здесь разделены три решения: какие механизмы покрыть, какие методы допустить к первичному сравнению (screening) и какие конфигурации продвигать по результатам validation. Покрытие семейства одним представителем не доказывает превосходство этого представителя внутри семейства.

## Почему именно восемь семейств

Восемь семейств взяты как **terminal families — конечные ветви современной taxonomy gradient-based multi-objective deep learning** из обзора Chen et al., *Gradient-Based Multi-Objective Deep Learning: Algorithms, Theories, Applications, and Beyond*. Для воспроизводимости классификации фиксируем [arXiv:2501.10945v1, 19 января 2025, рис. 1 и разделы III–V](https://arxiv.org/html/2501.10945v1). Это опубликованная структура механизмов, а не категории, придуманные постфактум под наши NDCG или удобные алгоритмы.

| Тип искомого решения в taxonomy | Конечная ветвь | Семейство в проекте |
| --- | --- | --- |
| Single solution | Loss Balancing | Балансировка функций потерь |
| Single solution → Gradient Balancing | Gradient Weighting | Взвешивание градиентов |
| Single solution → Gradient Balancing | Gradient Manipulation | Коррекция конфликтующих градиентов |
| Finite set of solutions | Preference Vector-Based | Конечный набор решений с preference vectors |
| Finite set of solutions | Preference Vector-Free | Конечный набор решений без явных preference vectors |
| Infinite set of solutions → Network Structure | Hypernetwork | Гиперсетевая аппроксимация множества решений |
| Infinite set of solutions → Network Structure | Preference-Conditioned Network | Сеть с preference conditioning |
| Infinite set of solutions → Network Structure | Model Combination | Комбинация моделей |

Получается **3 + 2 + 3 = 8**: Model Combination относится к infinite set, а Gradient Balancing — промежуточная ветвь. Цель — систематически покрыть все восемь механизмов именно этой классификации. Это не утверждение, что во всём MOO/MTL существует только восемь семейств: архитектуры MTL, эволюционные методы и другие классификации имеют иную область охвата.

Классифицируем механизм в данной постановке, а не название алгоритма навсегда: один solver может обучать отдельное решение и использоваться внутри гиперсети. Для ветвей infinite set проверяется параметризованное множество решений на конечной сетке предпочтений; точное восстановление всего Pareto front не предполагается.

## Протокол выбора представителей до новых результатов

**Дата фиксации этой редакции: 9 сентября 2026.** Результаты этапов 1–2 уже известны и сохранены в [RESULTS.md](RESULTS.md) и [MOO_EXPERIMENT_HISTORY.md](MOO_EXPERIMENT_HISTORY.md). Таблица ниже даёт содержательное обоснование первоначальных представителей, но не является их ретроспективной пререгистрацией. В прочитанных отчётах нет свидетельства, что все шесть критериев были письменно зафиксированы до этапа 1. Сейчас протокол фиксируется до чтения новых результатов challenger-screening; он не меняет историю прежнего отбора top-4.

На момент подготовки использован сохранённый challenger-срез `3993c648984b8460b81219fbcd47629458eb1d4b`: в [summary.json][challenger-summary] список `runs` пуст. Это граница доступных в Git результатов, а не проверка текущей очереди кластера. Уже зафиксированные правила запусков находятся в [DESIGN.md][challenger-design] и [config.yaml][challenger-config]; эта редакция их не пересматривает.

**Validation NDCG не используется для первоначального включения метода в screening.** То же относится к другим метрикам качества на наших validation/TEST: ни низкий исторический балл, ни ожидаемый высокий балл не являются основанием для допуска или исключения литературного кандидата. После фиксации состава и правил validation NDCG@10 используется для выбора checkpoint и последующего сравнения в пределах объявленного протокола.

| Критерий | Что фиксируем до просмотра новых результатов |
| --- | --- |
| **Family fidelity — соответствие семейству** | Основной механизм из статьи, его место в taxonomy и то, что сохраняет наша реализация. Различаем точное воспроизведение, адаптацию конкретного метода и проверку идеи семейства; перечисляем отклонения. Если механизм утрачен, результат не считается проверкой этого семейства независимо от NDCG. |
| **Scientific recognition — научная обоснованность** | Первичную статью, год, площадку и связь с обзором или последующими работами. Рецензируемая публикация и проверяемое описание алгоритма дают основание для включения; известность сама по себе не означает превосходство на KuaiRand. Для препринта явно указываем статус. |
| **Recency — актуальность** | Наряду с исходным методом рассматриваем более поздние работы и объясняем, какую его слабость они проверяют. Более новый год не даёт автоматического приоритета над fidelity и воспроизводимостью. Приведённые кандидаты — ограниченный литературный список, а не заявление о полном поиске всех работ на 2026 год. |
| **Reproducibility — воспроизводимость** | Доступность статьи и кода либо возможность проверяемой реализации; версии, исходный commit, зависимости и отклонения. До полноценного screening требуются проверки математического ядра и прохождения градиентов, затем smoke/sanity. Непроверенный перенос помечается как открытый вопрос, а не как exact reproduction. |
| **Compatibility with common TiM4Rec/MTL backbone — совместимость** | Общий `MultitaskTiM4Rec`, те же данные протокола B и пять задач: `rank/next_item`, `is_click`, `long_view`, `is_like`, `is_profile_enter`. Различия в adapters, числе моделей, охвате градиентов и правилах предпочтений объявляются явно; смена backbone или targets требует отдельного сравнения. |
| **Computational feasibility — вычислительная выполнимость** | Число моделей и параметров, стоимость градиентов/solver, память и бюджет запусков. Оценка и smoke определяют выполнимость; таймаут или сбой инфраструктуры не доказывает слабость семейства. Ограничение бюджета записывается до результатов, а не подбирается под желаемый исход. |

Порядок применения протокола:

1. По taxonomy составить литературный список внутри семьи и записать для каждого рассматриваемого кандидата источник, механизм, доступность реализации и ограничения переноса. Статус «не включён в этот раунд» не означает «хуже».
2. Проверить обязательные условия: сохраняется механизм, есть проверяемая реализация и перенос на общую постановку укладывается в объявленный бюджет. Научную обоснованность и актуальность использовать для выбора среди допустимых кандидатов; при сопоставимых основаниях предпочесть меньший объём отклонений от статьи и более проверяемый код. Не вводить сумму баллов с весами, подобранными по метрикам.
3. Зафиксировать initial representative, challenger или причину отсутствия challenger, ожидаемую проверку и ограничения вывода. Затем пройти проверки реализации и smoke/sanity; они проверяют корректность и выполнимость, не ранжируют методы по качеству рекомендаций.
4. До чтения результатов сохранить состав сравнения, версии кода, seeds, бюджет, нормализацию, рабочую точку, правило выбора решения/checkpoint и остановки. Поздние изменения оформлять новым датированным протоколом и отдельным сравнением, сохраняя прежние результаты.

## Семейства, литературные кандидаты и проверяемые основания

Литературная карта опирается на [список авторов обзора](https://github.com/Baijiong-Lin/Awesome-Multi-Objective-Deep-Learning) и первичные статьи по ссылкам. «Исходный представитель» означает реализацию этапа 1; «современный challenger» — конкретную более позднюю альтернативу в текущем раунде. Обоснование в предпоследнем столбце не использует наши метрики; его запись сейчас не доказывает, что именно такая формулировка существовала до исторических запусков.

| Семейство | Литературные кандидаты | Исходный представитель | Современный challenger | Основание до новых результатов | Что проверяет эксперимент |
| --- | --- | --- | --- | --- | --- |

| Gradient Weighting | MGDA, CAGrad, Nash-MTL, FAMO, FairGrad | [FAMO, NeurIPS 2023][famo] | Не назначен в этом раунде | Адаптивное взвешивание со сниженной стоимостью работы с градиентами подходит для общего MTL-backbone. MGDA/Nash-MTL/FairGrad остаются альтернативами; FAMO не объявляется самым новым методом. | Динамику весов и потерь, устойчивость и стоимость обучения вместе с validation-качеством. |
| Gradient Manipulation | PCGrad, GradDrop, GradVac | [PCGrad, NeurIPS 2020][pcgrad]; режим `ranking_anchored` | Не назначен в этом раунде | Проекция конфликтующих градиентов — понятный механизм с первичной публикацией; более поздний GradVac требует отдельного обоснования переноса. FERERO проверяет более позднюю формализацию предпочтений; сопоставление требует одинаковой семантики векторов и общих задач. | Управляемость предпочтениями, устойчивость solver и качество при замороженной рабочей точке; сохранится ли основание оставить EPO после сопоставимого screening. |

GradHV-style — локальная адаптация, поэтому нужен опубликованный современный set-based challenger с проверяемым ядром. | Различимость решений, качество набора и выбранной точки, стоимость; отдельно — влияние различий правил выбора GradHV и MosT. |
| Hypernetwork | PHN, PHN-HVI | [PHN, ICLR 2021][phn] → PHN-adapter | [PHN-HVI, AAAI 2023][phn-hvi] → PHN-HVI-adapter | Гиперсеть генерирует параметры по предпочтению. Общая adapter-параметризация позволяет исследовать multi-sample HVI при контролируемой архитектуре и стоимости. | Взаимодействие нескольких preferences в HVI, чувствительность модели к preference и качество; сравнение остаётся на уровне adapters. |
| Preference-Conditioned Network | You Only Train Once (ICLR 2020), COSMOS (ICDM 2021), Controllable Dynamic Multi-Task Architectures (CVPR 2022) | [COSMOS-style][cosmos] | Не назначен в этом раунде | Прямое conditioning представления на preference отделяет эту ветвь от генерации весов. Адаптация к TiM4Rec сохраняет общие задачи; наличие более поздних архитектур не делает их перенос автоматически сопоставимым. | Чувствительность представлений и ranking scores к preference, отсутствие схлопывания и качество на фиксированной сетке. |
| Model Combination | PaMaL (ICML 2023), LORPMAN (ICML 2024), PaLoRA (ICLR 2025) | [PaLoRA][palora] | Не назначен в этом раунде | Preference-взвешенная комбинация low-rank adapters даёт экономную реализацию комбинации моделей и более поздний литературный ориентир. Соответствие этой ветви — интерпретация механизма PaLoRA, а не утверждение о его наличии в версии обзора v1. | Различимость комбинаций, зависимость предсказаний от preference и качество с учётом числа добавленных параметров. |

Три challenger выбраны для проверки конкретных методологических разрывов: более поздняя preference-guided альтернатива EPO, опубликованный set-based метод вместо проверки только HV-идеи и усиление обучения гиперсети при прежнем adapter. Это не выбор трёх самых слабых строк по NDCG. Отсутствие challenger в остальных пяти строках ограничивает объём текущего раунда, но не закрывает внутри-семейное сравнение.

## Спорные пары и границы будущего вывода

Все три challenger реализованы как **адаптации**, что раскрыто в [DESIGN.md][challenger-design] и [provenance.yaml][challenger-provenance]. Проверки ядра не доказывают точное воспроизведение опубликованных результатов или перенос теоретических гарантий на TiM4Rec.

- **EPO / FERERO-adapter.** Проверяется preference-guided оптимизация на пяти прежних задачах. У FERERO объявлены перенос dual solver, shared-backbone Gram, внешний Adam и ограничение шага; согласование loss-ray не подменяется придуманными порогами качества задач. Новизна FERERO и исторический результат EPO не решают исход сравнения заранее.
- **GradHV-style / MosT-style.** Проверяется альтернативное совместное обучение конечного набора моделей без preference vector в оптимизаторе. MosT переносится из исходной постановки на minibatch-градиенты и Adam. Исторический GradHV выбирал solution по максимуму validation NDCG, MosT — по замороженному scalarized `rank_heavy` score. Поэтому разность итоговых NDCG сама по себе не является чистым эффектом алгоритма; для окончательного выбора нужен сопоставимый контроль с общим правилом выбора решения.
- **PHN-adapter / PHN-HVI-adapter.** Проверяется multi-sample HVI на той же adapter-параметризации, а не full-weight PHN. В дизайне явно указаны отличия sampling/cosine и расписания обучения. Генерация всех весов технически возможна на A100; adapter выбран ради контролируемого сравнения и параметрического бюджета. По этой паре нельзя отвергать всё гиперсетевое семейство или объявлять PHN-HVI точно воспроизведённым.

По [последнему сохранённому снимку][challenger-snapshot] от **8 сентября 2026, 23:05 МСК** повторные smoke `4313101`, `4313102`, `4313103` находились в PENDING. Предыдущие smoke завершились до запуска Python из-за отсутствия Git в PATH; [STATUS.md][challenger-status] сохраняет эту историю и указывает, что sanity/convergence ещё не отправлены. В прочитанном Git-срезе нет завершённых convergence-результатов и решения «заменить / оставить». Это датированный статус, не прогноз завершения и не live-проверка кластера.

Результаты challenger-экспериментов не должны менять перечисленные критерии, литературные основания или правила допуска. После завершения они могут изменить эмпирическое решение о представителе, с сохранением исходной таблицы и явным описанием ограничений.

## Когда допустим выбор по результатам

**Ни один метод не называется окончательным winner до завершения одинакового validation screening сравниваемых реализаций.** Под одинаковым screening понимаются общие данные, backbone/targets, политика seeds, правило выбора рабочей точки и checkpoint, нормализация, лимит эпох, early stopping и возможности настройки. Число моделей и фактическая стоимость раскрываются отдельно: одинаковый лимит эпох не означает одинаковые GPU-часы. Сбой, таймаут или неполный прогон не превращаются в проигрыш по качеству.

В текущем challenger-дизайне уже зафиксированы seed `2026` (для независимых моделей `2026+i`), нормализация по восьми TRAIN batches, отсутствие нового tuning, максимум `100` эпох, validation каждые `5` эпох, минимум `20` эпох и patience `3` проверки. Основная точка FERERO/PHN-HVI — `rank_heavy`; MosT выбирает solution по scalarized score с фиксированными scales и разрешением равенства по индексу, после чего checkpoint выбирается по validation NDCG@10. Полные значения и формулы — в [config.yaml][challenger-config].

Исторический этап 2 имел разное число завершённых trials; его результаты — дополнительный контекст, а не равный бюджет для challengers. Текущий раунд также не устраняет автоматически различие выбора solution у GradHV/MosT. До сопоставимого контроля допустимы описательные результаты и условный вывод о конкретной реализации, но не окончательный победитель семейства. Даже после такого screening вывод ограничен этим протоколом; универсальное превосходство и устойчивость по нескольким seeds требуют отдельных доказательств.

## Гигиена TEST: no TEST for selection

TEST не используется для выбора семейства, допуска метода, замены представителя, настройки гиперпараметров, выбора preference/solution, checkpoint или архитектуры. Для challenger-screening сохраняются `load_test_dataset=false`, `create_test_dataloader=false`, `evaluate_test=false`, `test_evaluation_count=0`. После фиксации финального метода TEST допустим только в заранее замороженной итоговой оценке, без возврата к подбору по его результатам.

Исторические TEST-воспроизведения базовых моделей в [RESULTS.md](RESULTS.md) остаются отдельными фактами: они не являются основанием нового MOO-отбора. Локальные проверки кода и parity не означают оценку на TEST split.

## Как читать эту таблицу

EPO показал лучший NDCG@10 на валидационной выборке в этапе 1: `0.0584`. Поэтому EPO, GradHV, COSMOS и PCGrad были переданы в этап 2 для настройки гиперпараметров. Это рабочее решение по итогам первичного отбора, а не доказательство, что остальные семейства не могут дать лучший результат при другой реализации или большем бюджете.

GradHV-style и COSMOS-style обозначены как адаптации под текущую MTL-постановку. PHN-adapter также является адаптацией: он проверяет идею гиперсетевого представления, но не претендует на точное воспроизведение всех деталей конкретной опубликованной реализации.
